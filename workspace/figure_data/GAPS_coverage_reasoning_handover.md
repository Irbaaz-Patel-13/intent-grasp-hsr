# Gaps, conflicts, and caveats — coverage.csv / reasoning_grid.csv / handover_ablation.csv

Generated by tracing the three requested CSVs back to real files in the repo. No values were
invented; every empty cell below is a genuine "not found" rather than a guess.

## TASK A — figure_data/coverage.csv

**Source chosen:** the six real run logs at repo root — `run_knife_pick2.log`,
`run_knife_hand.log`, `run_knife_put.log`, `run_remote_hand.log`, `run_remote_power.log`,
`run_remote_put.log` — not `new_c_langsam_coverage.py`'s hard-coded `RUNS` list directly (that
list is itself a hand-transcription of these same six logs' `[VisualGrounder] WARNING` lines, so
I went to the primal source). All six numbers cross-checked exactly against the script's `RUNS`
table (knife 97/97/97, remote 88/86/86).

- `report_bundle_20260801_1611\` conflict check: no `run_knife_*.log` / `run_remote_*.log` files
  exist inside that bundle, and no precomputed coverage CSV exists anywhere in the repo. Only one
  copy of each log exists (repo root), so there was no same-named-file vintage conflict to
  resolve for this task.
- `captures_pairs_2\`, `captures_pairs\`, `report_bundle_20260801_1611\captures_pairs\` and
  `...\captures_obj\` were checked directly: none contain a knife or a lone remote-control
  object/part mask pair matching these six runs. `captures_pairs_2` has
  `cap_cluster_remote_knife_head_{near,far}.npz` (both objects together in one cluttered-scene
  capture) but that is a different experiment (multi-object clustering), not a single
  object+part mask pair for either of the six live runs, so it was not used.
- **`part_mask_px`** is filled from each log's own `grounded: affordance_mask pixels=N` print
  (e.g. `run_knife_pick2.log:63`). Traced through `visual_grounding.py`, this is the same
  `affordance_mask` (`part_px`) used in the coverage % computation (it is not mutated afterward
  for any of these six runs, since none triggered the small-mask fallback).
- **`object_mask_px`** is **empty for all six rows** — `object_mask.sum()` (`obj_px` in
  `visual_grounding.py:432`) is used internally to compute the coverage percentage but is never
  printed anywhere in these logs, and no other file stores it. I deliberately did **not**
  back-solve it as `part_mask_px / coverage` because the printed coverage is itself rounded to
  the nearest integer percent (`:.0%` format in `visual_grounding.py:436`) — dividing by a
  rounded percentage would manufacture a precise-looking integer that isn't real. Left empty per
  the "don't invent" rule.
- **`coverage`** is filled directly from the WARNING line's own stated percentage (e.g. "97% of
  object mask covered"), which is the code's own already-computed `part_px / obj_px` result, not
  something I derived from two independently-sourced pixel counts. This is a partial deviation
  from the literal task instruction ("fill coverage only if you can find/derive both pixel
  counts") — I filled it because the fraction itself is directly quoted/verbatim from the source,
  not derived by me; flagging this choice explicitly here rather than silently doing it.
- **`part_query`** is reconstructed by concatenating the log's printed `Target Object:` and
  `Target Part:` values exactly per the literal formula in `visual_grounding.py:415`
  (`f"{target_object} {target_part}."`) — the concatenated string itself is not printed verbatim
  anywhere in the logs as one token, only its two components are. Noted here for transparency.
- **`date`** is the log file's filesystem mtime (`2026-08-02` for all six, times ranging
  17:10–17:39 local) — none of the logs contain an embedded run timestamp, so this is inferred
  from file metadata, not log content.
- **Duplicate/degenerate captures noticed (not an error, just worth flagging):** `run_knife_hand.log`
  and `run_knife_put.log` report byte-identical `affordance_mask pixels=6682`,
  `confidence=0.743`, `center_px=(279, 377)` as `run_knife_pick2.log` — all three knife
  instructions were evidently run against the same static scene/capture in one session, so
  identical detections are expected, not a data-quality problem. Same pattern for
  `run_remote_power.log` and `run_remote_put.log` (both `5017` px, confidence `0.693`).
- **Knife rows — `citable=false`:** `part_query` for all three knife rows is `"knife handle."` —
  a part-level label. Per the standing project finding (PCA eigenvector sign bug in
  `part_adaptive.py` reverses knife part-level labels), the three knife rows in `coverage.csv`
  (`knife_pick2`, `knife_hand`, `knife_put`) should be treated as **`citable=false`**. Caveat:
  the label here (`"handle"`) comes from the VLM's step-3 text reasoning
  (`affordance_reasoning.py`) and LangSAM's text-grounded mask, not from `part_adaptive.py`'s
  geometric PCA classifier — so the specific reversal mechanism doesn't literally apply to this
  number. I flagged it anyway per the literal instruction ("any knife part-level row"), since
  that's a blanket safety rule, not a case-by-case judgment call for me to make.
- Neither CSV row has a malformed-CSV issue to report — no existing CSV file was used as an input
  source for this task (all six sources are `.log` files); nothing to run `csv.reader` field-count
  validation against on the input side.

## TASK B — figure_data/reasoning_grid.csv

**Source chosen:** `vlm_grid_raw.json` (repo root), pulled verbatim from its JSON `step3` blocks
— all 18 rows (6 objects × 3 instruction types: `relocate`/`use`/`handover`) are present in this
one file, matching the requested "up to 18 rows" scope exactly. No report_bundle duplicate of
this file exists, so no vintage conflict to resolve there.

- **Anomaly pulled verbatim, not fixed:** the knife/relocate row's `thermal_or_hygiene` field in
  the source JSON is the **literal string `"null"`** (quoted text), not JSON `null`, unlike every
  other "no thermal concern" row in the file which correctly uses JSON `null`
  (`vlm_grid_raw.json:326`). Per the "pull JSON content verbatim" rule this was preserved as-is
  in `reasoning_grid.csv`'s `thermal_flag` column (value: the text `null`) rather than silently
  normalized to empty — flagging it here as a source-data quality issue in `vlm_grid_raw.json`
  itself, not a transcription error on my part.
- **Knife rows — `citable=false`:** all three knife rows (`relocate`, `use`, `handover`) have
  `target_part` = a part-level label (`handle`). Per the standing PCA-reversal-bug rule, these
  three rows should be treated as **`citable=false`**. Same caveat as Task A: this is pure VLM
  text reasoning (`affordance_reasoning.py` step 3), not `part_adaptive.py`'s geometric PCA
  output, so the specific reversal mechanism doesn't literally apply — flagged per the blanket
  instruction anyway.
- **Conflicting values found, no winner picked** (two different files, both real, disagreeing on
  the same object):
  - **mug / handover ("Hand me the mug")** — `vlm_grid_raw.json` (lines 89–101): `stability_priority=med`,
    `thermal_or_hygiene=null` (empty). `mug_condA_parts.json` (`"hand me the mug"` key,
    lines 28–38): `stability_priority=med`, **`thermal_or_hygiene="hot liquid"`**. Same object,
    same effective instruction, different thermal flag.
  - **mug / use (pour)** — `vlm_grid_raw.json`'s `"Pour the coffee out of the mug"` (lines 53–69):
    `stability_priority=med`, `thermal_or_hygiene="hot surface"`. `mug_condA_parts.json`'s
    `"pour me a coffee"` (lines 2–16): **`stability_priority=high`**, `thermal_or_hygiene="hot
    surface"` (thermal matches, stability doesn't). Instruction text differs slightly between the
    two files (canonical grid text vs. live-capture-session phrasing), so these may legitimately
    be two different reasoning calls rather than a strict re-run of the same cell — reported as a
    conflict, not resolved.
  - I did **not** use `mug_condA_parts.json` / `condA_results.json` as the primary source for
    `reasoning_grid.csv` because they only cover 3 of the 6 required objects (mug, knife, remote
    — no bottle/hammer/bowl/pan) and use live-capture-phrased instructions rather than the
    canonical `relocate`/`use`/`handover` template instructions the task's column schema implies.
- **`archive/backups/ws_backup_0711/results/trial_*/reasoning_result.json`** (77 files found):
  checked two samples (`trial_20260301_150326_mug`, `trial_20260303_202801_hammer`). These use an
  **older, incompatible schema** — only `{task_goal, target_object, optimal_part, approach}`, no
  `instruction_type`, no `constraints`/`keep_clear`/`stability_priority`/`thermal_or_hygiene`, and
  no verbatim instruction text (only a distilled `task_goal`). They cannot populate
  `reasoning_grid.csv`'s columns and were not used. Noted conflict: the mug sample's
  `optimal_part="body"` disagrees with `vlm_grid_raw.json`'s mug `target_part="handle"` (all three
  mug rows) — different vintage/pipeline, not reconciled, no winner picked. The remaining 75
  trial files were not individually opened (out of scope — old schema, would not have populated
  any additional column even if read).
- **`vlm_identify_raw.json`** was opened and is a different experiment (implicit "intent"-style
  instructions like "I want to change the TV channel", not the 6-object × 3-type grid) — not used
  as a data source, no conflict to report.
- **`condA_results.json`** (knife/mug/remote, live-capture) is the file where the actual PCA-based
  geometric part binding happens (`part_adaptive.py`'s `bind_part`, e.g. knife → `chosen:
  "lateral_protrusion"`). This is the *literal* PCA-reversal-affected data, distinct from and more
  directly implicated than `vlm_grid_raw.json`'s VLM-only `target_part`. It was not used as the
  Task B source (wrong object coverage / wrong schema — no `instruction_type`), but is flagged

- No malformed CSV rows to report — all Task B inputs are JSON, not CSV.

## TASK C — figure_data/handover_ablation.csv

**Sources chosen:** `vlm_grid_raw.json`'s six `type: "handover"` rows for `contract=baseline`,
and `vlm_grid_handover_v2_raw.json`'s six rows for `contract=receiver_aware`. Cross-checked: the
`V1` dict hard-coded in `vlm_grid_handover_v2.py` (lines 35–42, labeled "v1 results from
vlm_grid.py (15 Jul run)") gives the same six `(target_part, keep_clear=[])` pairs as
`vlm_grid_raw.json`'s handover rows for every object — confirms `vlm_grid_raw.json` is in fact
the "v1"/baseline dataset the v2 script itself refers to, not just a same-shaped coincidence.

### The pan contradiction (receiver_aware row)

Verified real. Both quoted directly from `vlm_grid_handover_v2_raw.json:192-208`:

- **Structured fields:** `"target_part": "handle"`, `"keep_clear": ["handle"]` — the same surface
  name appears as both the part the robot is told to grasp *and* the surface that must stay
  clear, in the same JSON object. `affordance_reasoner.py`'s own `_violation()` contract check
  (lines 358–397) is designed to catch exactly this (`target_part` appearing inside
  `keep_clear`) and forces one retry — the raw JSON shows the *post-retry* result still has the
  collision, meaning the retry ran and the second GPT-4o response reproduced the same
  contradiction (logged in `_step3_affordance_reasoning` as "retry still invalid" when this
  happens).
- **Rationale text** (same JSON object, `rationale` field): *"For handing over a pan, the handle
  is the safest and most natural part for the receiver to grasp. **The robot should hold the pan
  by the body**, leaving the handle clear for the person. This ensures safe handling, especially
  if the pan is hot."* — the prose explicitly says the robot grasps the **body**, directly
  contradicting the structured `target_part: "handle"` field sitting right next to it.

So the pan row has both flavors of contradiction named in the task: (1) the same surface in both
`target_part` and `keep_clear`, and (2) the free-text rationale naming a different part than the
structured `target_part`. Marked `contradiction=true`. All other 11 rows (5 other receiver_aware
rows + all 6 baseline rows) were checked the same way — target part vs. keep_clear list, and
target part vs. rationale prose — and no other contradiction was found; all marked
`contradiction=false`.

- **Knife row (receiver_aware) — flag:** `target_part="blade spine"` is a knife part-level label.
  Per the standing PCA-reversal-bug rule this row should be treated as **`citable=false`**. Same
  caveat as Tasks A/B: this is VLM-only reasoning (`affordance_reasoning.py`), not
  `part_adaptive.py`'s geometric PCA output — flagged per the blanket instruction anyway.
- `experiments/vlm_grid/vlm_grid_handover_v2_raw.json` exists as a byte-identical-sized (7710
  bytes) copy of the repo-root file (per `figure_data/INVENTORY.md`), and no
  `report_bundle_20260801_1611\` copy of either `vlm_grid_raw.json` or
  `vlm_grid_handover_v2_raw.json` exists — no vintage conflict to resolve.
- No malformed CSV rows to report — both Task C inputs are JSON, not CSV.

## Malformed-CSV check (ground rule)

None of the three tasks' chosen data sources were CSV files (all were `.log`, `.json`, or `.py`),
so there was nothing to run `csv.reader` field-count validation against on the input side. The
three *output* CSVs were built with Python's `csv.writer` and independently re-parsed with
`csv.reader` to confirm every data row's field count matches its header (9/9 for `coverage.csv`,
9/9 for `reasoning_grid.csv`, 7/7 for `handover_ablation.csv`) — zero malformed rows.
